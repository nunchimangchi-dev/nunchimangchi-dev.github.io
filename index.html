Go · AI agent orchestration · privacy automation

What it does: An AI-driven data broker opt-out orchestrator. It seeds a queue of 85 real U.S. data brokers, walks each one through an opt-out strategy suited to that site, and tracks progress on a real-time dashboard — built as a genuine attempt at solving a real privacy problem with an AI agent doing the meaningful decision-making, not a script with an LLM bolted on.

The real decision: Strategy 1 (a TruthFinder affiliate cascade covering 7 broker properties through one form submission) shipped first on purpose — highest coverage for the effort, and a way to validate the whole pattern (Claude's vision capability confirming the opt-out from a post-submit screenshot) before committing to the other five.

Current state: 1 of 6 strategies built and tested against the real site; the rest are scoped and registry-seeded, not started — the README says so directly.

Next.js · TypeScript · Prisma · Google OAuth

What it does: A fitness/coaching app — workouts, meal tracking, progress history, and a "wagers" feature (commitment contracts against your own goals, with a built-in safety guardrail capping how aggressive a weight-loss target can be). Next.js specifically because it was the fastest path to something usable on a phone browser, not a default choice.

The real decision: Building the wagers feature surfaced a real bug — the tables tracking weight and streaks had no per-user scoping at all, invisible until a feature needed to read that data correctly. Fixing it meant a hand-written SQL migration to safely backfill existing data before making the column required, plus a new auth gate on a page that didn't have one before.

Current state: Real Google OAuth with an allowlist gate, CI on every PR, production deployment over a private tailnet. Also the validation case for skyrise — proving the dev environment on something real.

chezmoi · fish · tmux · infrastructure

What it does: A repeatable bootstrap for a dev environment — git/GitHub identity, tmux, fish shell, Bitwarden, and chezmoi-managed dotfiles — applied identically across a Linux server and a MacBook from one source of truth.

The real decision: chezmoi specifically because it reconciles real Linux/macOS differences (paths, package managers) from one source of truth, rather than maintaining two configs. That choice paid off directly: the shared fish config used to silently depend on a Linux-only package, invisible until the second host actually needed it — caught and fixed before it caused a real problem, not after.

Current state: Both hosts live on the same config. Not a toy dotfiles repo — it's the actual infrastructure the other two projects are built and deployed on, with a public build-log dashboard tracking what's done vs. pending.

How these get built

All three projects are built with Claude Code doing a real share of the implementation work. My part is scoping the actual approach and reviewing it before code gets written, then verifying the result for real — running it, clicking through it, checking the database directly — rather than trusting a clean build as proof it works.

The wagers data-scoping bug on droppdd (see above) is a fair example of why that verification step matters: a prompt asked for a feature, not a schema audit, and the tables it needed to read turned out to be broken in a way that only showed up once you actually tried to use them correctly. The tools generate code quickly — catching what's actually wrong with it, and making the calls on data model and security tradeoffs, is the part that doesn't get automated away.
