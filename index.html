Next.js · TypeScript · Prisma · Google OAuth · Gemini AI

What it does: A live, invite-only beta fitness accountability app for keto/OMAD training: guided workouts, AI-generated meal plans (Gemini, with the model's output treated as untrusted input and validated the same as any client form data), daily check-ins, peer-to-peer wager challenges with real stakes, and a leaderboard that only ever shows relative progress — never a user's raw weight.

The real decision: A systematic, persona-driven audit — walking the live app end-to-end as a cold first-time user, one surface at a time — surfaced a genuinely serious latent bug: the streak and weight-progress tracking had silently never worked past a user's first day, invisible until someone asked the obvious question a feature prompt hadn't: "how would a user actually update their weight?" Fixed with a real daily check-in flow, after confirming the product definition of a "streak" first rather than guessing at it.

Current state: Live in an active invite-only beta with real outside users. Required unique usernames, peer wagers, a leaderboard, and a full admin panel — including a GDPR/CCPA-style data export & deletion flow built specifically to back a real, authored Privacy Policy. Runs on its own network-isolated host behind a Cloudflare Tunnel with zero inbound ports opened on the network. Also the validation case for skyrise — proving the dev environment and hosting pattern on something real.

Go · AI agent orchestration · privacy automation

What it does: An AI-driven data broker opt-out orchestrator. It seeds a queue of 85 real U.S. data brokers, walks each one through an opt-out strategy suited to that site, and tracks progress on a real-time dashboard — built as a genuine attempt at solving a real privacy problem with an AI agent doing the meaningful decision-making, not a script with an LLM bolted on.

The real decision: Strategy 1 (a TruthFinder affiliate cascade covering 7 broker properties through one form submission) shipped first on purpose — highest coverage for the effort, and a way to validate the whole pattern (Claude's vision capability confirming the opt-out from a post-submit screenshot) before committing to the other five.

Current state: 1 of 6 opt-out strategies built and tested against the real site; the rest are scoped and registry-seeded, not started — the README says so directly. The dashboard itself went further: a full visual redesign, real public deployment on its own isolated host behind Cloudflare Access, and an admin panel (viewer/admin roles, PII profile management, run control) built on Access's own identity rather than a second login system.

skyrise

View on GitHub →

chezmoi · fish · tmux · Proxmox · Cloudflare Tunnel

What it does: Started as a repeatable dev-environment bootstrap — git/GitHub identity, tmux, fish shell, Bitwarden, chezmoi-managed dotfiles — applied identically across a Linux server and a MacBook from one source of truth. Has since grown into a real self-hosted hosting platform on top of that same foundation.

The real decision: chezmoi specifically because it reconciles real Linux/macOS differences (paths, package managers) from one source of truth, rather than maintaining two configs. That choice paid off directly: the shared fish config used to silently depend on a Linux-only package, invisible until the second host actually needed it — caught and fixed before it caused a real problem, not after.

Current state: A Proxmox hypervisor behind a hardware firewall, with every public-facing service on its own network-isolated host, exposed only through a Cloudflare Tunnel — zero inbound ports opened on the home network. Not a toy dotfiles repo — it's the actual infrastructure droppdd and unbrokerrdd are built and deployed on, tracked on a public build-log dashboard showing what's done vs. pending.

How these get built

All three projects are built with Claude Code doing a real share of the implementation work. My part is scoping the actual approach and reviewing it before code gets written, then verifying the result for real — running it, clicking through it, checking the database directly — rather than trusting a clean build as proof it works.

droppdd's streak-tracking bug (see above) is a fair example of why that verification step matters: a feature prompt asked for a wager system, not a schema audit, and the data it needed to read turned out to be broken in a way that only showed up once someone actually asked how a real user would use it day-to-day. The tools generate code quickly — catching what's actually wrong with it, and making the calls on data model, security, and product tradeoffs, is the part that doesn't get automated away.
