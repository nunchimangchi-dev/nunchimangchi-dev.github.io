Any content changes need to stay grounded in what's actually true about

## What this page is

Read `index.html` and `style.css` in this repo directly — that's the
current, real content, not a draft. It's a portfolio landing page linked
from a resume, tying together three public GitHub repos
(`nunchimangchi-dev/skyrise`, `nunchimangchi-dev/droppdd`,
`nunchimangchi-dev/DATABROKER.deep`). If you have live web access, the
page is also published at https://nunchimangchi-dev.github.io/ — feel free
to check how it actually renders, but note whether you were able to
(don't assume you saw it render correctly if you only read the source).

## Purpose — read this before benchmarking anything

The point of this page is to demonstrate continued relevance and technical
currency during an employment gap — proof of active, real, shipped work,
not just claims on a resume. It is explicitly **not** trying to reposition
the author as something they're not.

Two audiences read this page, and they should NOT be benchmarked the same
way:

- **Director-level readers** (Director of IT, VP Eng, similar) are
  expected to intuitively understand and value what's here as-is — a
  senior technical reader recognizes real, current, hands-on work when
  they see it, without needing it translated into leadership-scope
  language. Don't optimize the page's voice for this audience; they're
  assumed to "get it" already.
- **EM (Engineering Manager) / TPM (Technical Program Manager) readers are
  the actual benchmark target.** This is the audience whose expectations
  actually matter for how this page should read, look, and be structured.
  If you have live search/web access, find and reference real examples of
  how people in EM/TPM roles (or candidates targeting those roles) present
  personal portfolios/project pages — what tone they use, how they
  balance "I built this" (hands-on/IC-coded) against "I drove this"
  (scope/ownership-coded), what visual conventions are common, what's
  missing or unusual about pages built by ICs who haven't had to think
  about EM/TPM audience expectations before.

## What to actually deliver

Write your findings to `docs/GEMINI-TONE-REVIEW-FINDINGS.md` in this repo
(new file, don't touch the two content files). Cover:

1. **Tone/wording** — does the current voice read as EM/TPM-relevant, or
   does it read purely IC/builder-coded in a way that undersells scope or
   ownership an EM/TPM reader would look for? Be specific — quote the
   actual lines you're reacting to, don't give abstract advice.
2. **Structure** — is anything missing that EM/TPM-focused portfolios
   commonly include (e.g. how technical decisions get made, how work gets
   scoped/prioritized, cross-functional or process elements) that this
   page doesn't touch at all, given it's currently framed around three
   solo-built projects?
3. **Visual presentation** — how does the current dark/light card-based
   layout compare to what you find in real EM/TPM-oriented portfolios?
   Concrete, not vague ("more whitespace" is not useful; cite what you
   compared it to and why).
4. **Cite what you actually found** — if you have real web access, name
   the kinds of sources/examples you looked at (even generically, e.g.
   "personal sites of several EM candidates on X platform") rather than
   presenting recommendations as if from nowhere. If you don't have live
   web access for this pass, say so explicitly rather than presenting
   trained-knowledge impressions as live research.

Prioritized list at the end: what's actually worth changing vs. what's a
minor nice-to-have. We'll decide together what to act on.
